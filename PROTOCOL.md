# Протокол управления D-Link DIR-825ACG1

Разбор недокументированного API прошивки «anweb». Всё описанное получено чтением JavaScript веб-интерфейса и проверено запросами к живому устройству.

**Прошивка 3.0.7**, сборка от 8 декабря 2021, аппаратная ревизия G1. На других версиях протокол может отличаться.

Официальной документации на этот интерфейс не существует. D-Link ничего о нём не обещал и вправе изменить его в любом обновлении.

---

## Как это выяснялось

Веб-интерфейс — приложение на AngularJS, его исходники отдаются без авторизации. Это и есть основной источник:

```
http://192.168.0.1/autoconf.js                     параметры сборки, включая модель
http://192.168.0.1/apps/admin/config.js            список страниц и их контроллеров
http://192.168.0.1/concat?type=js&path=admin/js_list        код приложения
http://192.168.0.1/concat?type=js&path=admin/lib_js_list    библиотеки и конвертеры данных
http://192.168.0.1/apps/admin/pages/<страница>/ctrl.lazy.js контроллер конкретной страницы
```

Файлы минифицированы, но не обфусцированы: имена функций и полей сохранены. Полезные точки входа для поиска — `somovd` (клиент JSON-RPC), `authDigest` (авторизация), `rpcs` (номера конфигураций), названия страниц из `config.js`.

## Авторизация

Схема — HTTP Digest MD5 с `qop=auth`, но с нестандартной асимметрией, на которой легко споткнуться.

**Вызов приходит в заголовке `anweb-authenticate`:**

```
HTTP/1.1 401 Unauthorized
Anweb-Authenticate: Digest qop="auth", realm="domain", nonce="6245488"
Anweb-Auth-Try-Count: 5
Anweb-Auth-Try-Count-Remain: 5
Set-Cookie: device-session-id=...
```

**Ответ отправляется в обычном `Authorization`**, плюс отметка о повторе:

```
Authorization: Digest username="admin", realm="domain", nonce="...", uri="/jsonrpc",
               response="...", qop=auth, nc=00000001, cnonce="..."
anweb-repeat-request: true
```

Отвечать в том же заголовке, откуда пришёл вызов, бесполезно — роутер молча вернёт 401.

**Вычисления стандартные по RFC 2617:**

```
HA1      = md5(username : realm : password)
HA2      = md5(METHOD : uri)
response = md5(HA1 : nonce : nc : cnonce : qop : HA2)
```

`uri` в `HA2` — путь без строки запроса. Для `POST /jsonrpc` это `md5("POST:/jsonrpc")`, для `GET /devinfo?area=...` — `md5("GET:/devinfo")`.

⚠️ **Пять неудачных попыток — временный бан.** Подбирать пароль перебором нельзя, счётчик возвращается в заголовке `Anweb-Auth-Try-Count-Remain`.

## JSON-RPC

Единственная точка: `POST /jsonrpc`. Тело — объект или массив объектов JSON-RPC 2.0.

| Метод | Параметры | Назначение |
|---|---|---|
| `read` | `id` | прочитать конфигурацию |
| `write` | `id`, `data`, `pos`, `save` | записать |
| `remove` | `id`, `data`, `pos`, `save` | удалить запись списка |
| `cmd` | `id` | команда устройству |

Команды `cmd`: **20** — сохранить конфигурацию во флеш, **6** — перезагрузка, **8** — сохранить и перезагрузить, **10** — сброс к заводским настройкам.

Пример чтения:

```json
{ "jsonrpc": "2.0", "method": "read", "params": { "id": 74 }, "id": 1 }
```

Успешный ответ содержит `result.status = 20` и `result.data`. Иной `status` означает отказ, причём поле `error` при этом может отсутствовать — проверять надо оба.

### Удаление записи списка

`remove` устроен симметрично `write`: в `data` кладётся тот же контейнер, что и при записи, а `pos` указывает номер удаляемой записи.

```json
{ "jsonrpc": "2.0", "method": "remove",
  "params": { "id": 42, "pos": 3, "save": true,
              "data": { "5G_MacFilterList": { "mac": "AA:BB:CC:DD:EE:03",
                                              "hostname": "phone", "active": true } } },
  "id": 1 }
```

Формат восстановлен по клиентскому коду и проверен на устройстве: сам интерфейс помечает запись суффиксом в своей внутренней модели и отправляет пакет изменений при сохранении, поэтому одиночного вызова в его коде не встречается.

### Сохранение и флаг «конфигурация изменена»

`write` без `save: true` применяет значение, но не пишет во флеш. Роутер при этом считает рабочую конфигурацию расходящейся с сохранённой и показывает в интерфейсе требование сохранить вручную.

Разумный компромисс: промежуточные записи с `save: false`, одна команда `cmd id:20` в конце операции. Это уменьшает износ флеш-памяти и не оставляет висящего флага.

## MAC-фильтр межсетевого экрана (74)

Действует на весь мост: и на Wi-Fi, и на проводные подключения. Блокирует маршрутизацию трафика, но не мешает устройству оставаться в сети и общаться с соседями по локальной сети.

`data.macfilter` — массив. **Нулевой элемент задаёт политику по умолчанию, а не правило:**

```json
{ "id": 0, "state": false, "mac": null, "enable": "DROP" }
```

`state: false` — разрешать всё (чёрный список), `state: true` — запрещать всё (белый список). Отличительный признак этого элемента — `mac: null`.

Остальные элементы — правила:

```json
{ "id": 3, "state": true, "enable": "DROP", "mac": "AA:BB:CC:DD:EE:01", "hostname": "" }
```

`state` — включено ли правило, `enable` — действие (`ACCEPT` или `DROP`).

### Подводные камни

**Новое правило пишется с `pos: -1`** — это «добавить в конец», позицию выбирает прошивка. Существующее правило перезаписывается со своей позицией в массиве.

**На устройстве со сброшенными настройками массив пуст полностью**, включая элемент политики. Если просто дописать туда первое правило, оно займёт нулевую позицию и станет политикой по умолчанию — а при `state: true` это означает «запрещать всё». От сети отвалятся сразу все устройства, включая то, с которого выполнялась настройка, и восстановление останется только через кнопку Reset.

Правильный порядок: сначала явно записать элемент политики на позицию 0, затем добавлять правила.

## MAC-фильтр Wi-Fi (42 и 39)

Действует только на беспроводных клиентов и блокирует саму ассоциацию с точкой доступа — устройство не может подключиться к сети. Проводные подключения не затрагивает.

Поля задаются отдельно для каждого диапазона, префикс — пустой для 2,4 ГГц и `5G_` для 5 ГГц:

```json
{
  "AccessPolicy": "0",      "MacFilterList":    { "max_instance": 0 },
  "5G_AccessPolicy": "0",   "5G_MacFilterList": { "max_instance": 0 },
  "MaxNumMacFilter": 0,     "SupportHotApply": true
}
```

`AccessPolicy`: **0** — фильтр выключен, **1** — пускать только перечисленных (белый список), **2** — запрещать перечисленных (чёрный список).

`MacFilterList` — не массив, а объект, где имя свойства это номер записи:

```json
{
  "max_instance": 5,
  "1": { "mac": "AA:BB:CC:DD:EE:01", "hostname": "laptop", "active": true },
  "4": { "mac": "AA:BB:CC:DD:EE:02", "hostname": "phone", "active": true },
  "5": { "mac": "AA:BB:CC:DD:EE:03", "hostname": "desktop", "active": true }
}
```

Номер записи — это её `pos`. Новые добавляются с `pos: -1`, как и в конфигурации 74; существующая удаляется методом `remove` со своим номером.

⚠️ **Номера — устойчивые идентификаторы, а не индексы массива.** Проверено на устройстве: после удаления записи остальные сохраняют свои номера, освободившийся номер повторно не выдаётся, а новая запись получает следующий по счётчику. Ряд `1, 4, 5` в примере выше — обычное состояние списка, прошедшего несколько правок.

Отсюда два следствия. Позицию нельзя вычислять по порядку записей — её нужно брать из имени свойства. И порядок удаления нескольких записей значения не имеет: сдвига, из-за которого пришлось бы идти с конца, здесь нет.

`max_instance` — значение того самого счётчика, то есть наибольший когда-либо выданный номер, а не количество записей. В примере записей три, а счётчик равен пяти.

Поле `MaxNumMacFilter` на проверенной прошивке равно нулю — ограничения на длину списка роутер не сообщает.

### Курсор выбора сети

Конфигурация 42 адресует не диапазон целиком, а **одну сеть внутри него**: роутер умеет держать в каждом диапазоне несколько сетей, включая гостевую, и у каждой свой фильтр. Какую именно — задаёт курсор в конфигурации 39:

```json
{ "jsonrpc": "2.0", "method": "write",
  "params": { "id": 39, "data": { "mbssidCur": 1 }, "save": false }, "id": 1 }
```

Для 5 ГГц поле называется `5G_mbssidCur`. Номера сетей и их количество берутся из конфигурации 35: `mbssidNum`, `mbssid[]` с полями `SSID` и `BSSID`. Если гостевых сетей нет, номер всегда `1`.

Чтение конфигурации 39 бесполезно — она ведёт себя как приёмник команды, а не как хранилище.

⚠️ **При одной сети в диапазоне курсор не нужен вовсе — ни для чтения, ни для записи.** Штатный интерфейс ставит его перед каждой операцией, и повторять это за ним заманчиво, но проверка на устройстве показала:

- ответ на `read` конфигурации 42 побайтово одинаков до и после установки курсора и содержит поля **обоих** диапазонов сразу — `AccessPolicy` вместе с `5G_AccessPolicy`, оба списка адресов;
- `write` и `remove` без курсора попадают ровно в тот диапазон, чей префикс стоит в имени поля: запись в `MacFilterList` легла в 2,4 ГГц, в `5G_MacFilterList` — в 5 ГГц, без перекрёстных эффектов.

То есть диапазон задаёт префикс поля, а курсор различает сети внутри него. Пока сеть одна, он всегда указывает на неё, и каждая его установка — это лишний запрос, а на пути чтения ещё и флаг «конфигурация изменена» после операции, которая ничего не меняла.

Проверялось на устройстве с одной сетью в каждом диапазоне. Появится гостевая — курсор понадобится снова, и тогда без него операция уйдёт не в ту сеть молча.

### Порядок операций

Штатный интерфейс сначала устанавливает политику, затем добавляет адреса. Для белого списка это опасно: между двумя командами политика уже «пускать только из списка», а список ещё пуст — сеть закрыта для всех.

Безопаснее наоборот: сначала наполнить списки на обоих диапазонах, последними командами включить политику. Сбой на любом шаге тогда оставляет фильтр выключенным.

**Настройки Wi-Fi (конфигурация 35) при этом трогать не нужно** — там лежат пароли сетей, и записывать туда ради фильтра ничего не требуется.

### Файл списка и список на роутере

Белый список хранится в `whitelist.json`, а `sync` приводит роутер в соответствие с ним: добавляет недостающие адреса и удаляет лишние. Файл — источник истины, и это верно ровно до тех пор, пока файл есть.

На новом компьютере его нет: в репозиторий он не попадает, первичная настройка его не создаёт. Прочитать отсутствующий файл как пустой список — значит показать пустую таблицу, а первая же синхронизация вычистит с роутера всё, что там было. Ошибка тихая: до включения белого списка она ничего не ломает и обнаруживается позже, когда список включают и половина устройств не подключается.

Поэтому, не найдя файла, окно выбора устройств читает отметки прямо из конфигурации 42: перебирает `MacFilterList` и `5G_MacFilterList` и смотрит, в скольких списках встретился адрес. В обоих — `both`, в одном — соответствующий диапазон. Ровно так же диапазон и записывается в файл, поэтому список, собранный с роутера, совпадает с сохранённым ранее файлом — проверено сличением на четырёх записях, включая все три сочетания.

Лишнего запроса это не стоит: конфигурация 42 уже прочитана ради строки состояния. Само чтение файла не создаёт — он появляется при первом сохранении или при включении списка, когда его требует `wifi-whitelist.ps1`.

## Сведения о состоянии: `/devinfo`

`GET /devinfo?area=<области через |>&need_auth=1`, авторизация та же, `HA2 = md5("GET:/devinfo")`.

| Область | Содержимое |
|---|---|
| `client` | сведения о самом запрашивающем: MAC, IP, интерфейс, SSID, диапазон |
| `version` | модель, версия прошивки, дата сборки, ревизия, серийный номер, uptime |
| `187` | клиенты локальной сети: MAC, IP, `name` (`WLAN` или LAN-порт), hostname, флаги |
| `34` | аренды DHCP: MAC, IP, hostname, `vendorid`, остаток аренды |
| `42` | текущее содержимое MAC-фильтров Wi-Fi |
| `64` | беспроводные клиенты: диапазон, SSID, режим, уровень сигнала, время в сети |

Несколько областей запрашиваются одним запросом, разделитель — вертикальная черта: `area=187|34|64`. Ответ содержит по свойству на каждую область.

Числовые области соответствуют номерам конфигураций. Флаг клиента `reachable` означает активность, `stale` — что устройство давно не отвечало.

Без параметра `area` возвращается ошибка `Can't find 'area' parameter`.

### Чем области отличаются на практике

⚠️ **Область 187 отдаёт строку на каждый IP-адрес, а не на устройство.** Из-за IPv6 у одного телефона легко набирается восемь строк с одинаковым MAC и разными адресами. Список нужно сворачивать по MAC, иначе он выглядит длиннее реальности в несколько раз.

Три области дополняют друг друга, и ни одна не заменяет остальные:

- **187** — кто активен прямо сейчас и через что подключён. Спящий телефон отсюда исчезает.
- **34** — все, кто подключался за время аренды (сутки). Единственный способ увидеть выключенное устройство. Поле `vendorid` подсказывает систему: `android-dhcp-15`, `MSFT 5.0`.
- **64** — только беспроводные. Единственный надёжный признак того, что устройство именно на Wi-Fi, и единственный источник диапазона. Адреса здесь в верхнем регистре, в остальных областях — в нижнем.

Отличить Wi-Fi от витой пары можно так: присутствие в области 64 означает Wi-Fi; в области 187 поле `name` содержит `WLAN` для беспроводных и имя порта для проводных. Для устройства, известного только по аренде DHCP, тип подключения неизвестен.

### Флаг reachable и почему присутствия три, а не два

⚠️ **`stale` не означает «устройства нет».** Область 187 — это кэш соседей, и флаг говорит лишь о том, подтверждалась ли связь недавно. Проверено: выключенный компьютер какое-то время висит там именно со `stale`, а тихий, но подключённый — тоже. Приравнивать `stale` к присутствию нельзя (получите «в сети» у только что выключенного), к отсутствию тоже (получите «нет в сети» у молчащего).

Отсюда три уровня уверенности вместо напрашивающихся двух:

| Признак | Что значит |
|---|---|
| есть в области 64, либо в 187 с `reachable` | связь подтверждена |
| есть в 187 только со `stale` | роутер помнит устройство, связь не подтверждена |
| только аренда DHCP в области 34 | в списке клиентов его нет вовсе |

Более точного признака для проводных устройств прошивка не даёт: отдельной области с состоянием LAN-портов нет. Проверены шесть кандидатов — `net` отдаёт интерфейсы самого роутера, `180` таблицу соединений, `206` IGMP, `267` каналы Wi-Fi, `interface` и `device` пусты.

### Случайные MAC-адреса

К протоколу роутера отношения не имеет, но нужно всякому, кто пишет правила по адресам. Признак случайного адреса — **второй младший бит первого байта**, в стандарте IEEE он называется «locally administered»: ноль означает адрес, выданный изготовителем сетевой карты, единица — назначенный самим устройством. В шестнадцатеричной записи первый байт такого адреса оканчивается на 2, 6, A или E.

Бит говорит о свойстве адреса, а не о настройке устройства, и потому не различает два случая:

- **постоянная рандомизация** — адрес придуман один раз для конкретной сети и переиспользуется; на практике стабилен, пока сеть не «забыть» и устройство не сбросить. Так по умолчанию ведёт себя Android начиная с десятой версии;
- **непостоянная** — адрес меняется регулярно.

То есть по биту можно сказать «адрес может смениться», но не «адрес меняется». Отличить одно от другого можно только наблюдением за тем, как долго адрес держится.

## Резервная копия конфигурации

Скачивание идёт через `GET /config_load`, но одного этого запроса недостаточно: интерфейс сначала выполняет подготовительный вызов, формирующий файл. Без него возвращается страница-заглушка вместо конфигурации. Этот вызов не разбирался — резервную копию проще сделать из веб-интерфейса, раздел **Система → Конфигурация**.

## Прочие наблюдения

Веб-интерфейс отдаёт заводские учётные данные прямо в `autoconf.js`, в открытом виде — это константы сборки прошивки, одинаковые для всех устройств модели, а не текущий пароль. При первой настройке мастер требует его сменить.

Сессия веб-интерфейса истекает через 5 минут бездействия (`logoutTime`), что заметно при отладке через браузер.

Каждая операция записи расходует ресурс флеш-памяти. Для ручных переключений это несущественно, для автоматических циклов — нет.
